Quillix

The problem

Indian small businesses file GST returns every month, and in practice their chartered accountant does it — and a wrong return is the accountant’s name on the line. Quillix sits between a client’s day-to-day billing and the two systems that must both be satisfied: the GST portal and Tally, where the books live.

  • Purchase bills arrive as scans of varying quality and are re-typed line by line — HSN codes, per-line GST rate, GSTINs.
  • Books are reconciled against the portal’s GSTR-2A/2B by eye, so a missing supplier invoice only shows up when input credit stops adding up.
  • Moving data into Tally is a manual export/import round-trip; Tally rejects unbalanced vouchers and unknown ledgers.
  • A firm runs dozens of clients at once, so every client’s data has to stay isolated and every role limited to what it should see.

What I built

One workspace for a whole practice: a firm-level cockpit across all clients, and a full bookkeeping-to-filing workflow inside each one.

Firm cockpit

An exception-first dashboard: a ranked worklist of what needs attention — unfiled returns, unbilled clients, unusable GSTINs, unreconciled records — over a roster of every client.

Sales, purchases & ITC

Per-line GST with intra/inter-state detection from GSTIN state codes, credit and debit notes, recurring invoices, and input-tax-credit classification per line.

Bill OCR

Upload up to ten bills; a background job extracts header fields, line items and per-rate summaries into a side-by-side review screen with confidence flags.

GST returns

GSTR-1 tables with portal-format JSON export and a filed-period lock, GSTR-3B computation, and GSTR-2A/2B reconciliation against the books.

Tally export

Voucher export with bottom-up balancing, master ledgers ensured first, and batched sends; a Windows shell adds a live bridge to TallyPrime on the same machine.

Notice Reply

Upload a GST or income-tax notice and get a summary and a response plan — with the client’s figures filled in on the device, never sent to the model.

Firms, roles & audit

Partner, manager and associate roles with per-client access, an approval workflow for edits and deletes, and a server-written audit trail clients cannot forge.

Built for the user

In-app help and guided tours in English and Tamil, a dark mode, a command palette, and a separate operator console for running the platform.

How it works

The browser talks to Firestore directly, and security rules are the real authority. Heavy lifting happens on the server in triggers and schedulers, which keep derived documents so pages never have to read a client’s whole book.

Sign-in + 2nd factor Firm & role Security rules Per-record writes Server triggers Derived documents Fast pages
ClientReact 18 and Vite, with hand-written CSS and a lazy-loaded page per route. A persistent, multi-tab Firestore cache keeps it usable on a flaky connection.
Data modelEverything is per-document under firms/{firm}/stores/{client}. A sale is one document per invoice, with the lines inside it. A migration off single large documents removed Firestore’s 1 MB document ceiling and write contention.
SecurityFirestore and Storage rules enforce firm and client scoping and role limits; privilege-escalation guards stop a user creating or promoting people outside their remit. Rules are tested against the emulator, and the client is never trusted.
BackendCloud Functions (Node 22): callables for OCR, lookups, encryption and email, Firestore triggers for the audit trail and integrity flags, and schedulers for recomputation and backups.
Derived dataMonthly summaries, receivables and payables, and stock levels are kept by the server and recomputed from the documents — never from running totals, so a missed trigger heals itself. The dashboard no longer reads the book at all.
IntegrationsGemini and Vertex AI, GSTIN lookup and filing-status services, transactional email, and TallyPrime over a local bridge.

The AI layer

Three independent, single-shot model calls — deliberately not an agent. Each one is a structured request with a clear job and a clear failure mode.

Bill upload Duplicate check (hash) Cheap model read Low confidence? → 2nd model Human review Reviewed result cached
Bill OCREvery bill goes to a cheap Gemini model first, which also rates its own confidence per field. Only when a critical field — a GSTIN, an invoice number, a total or a tax amount — falls below a confidence floor does a second model read it again. Results stream into the review screen as they arrive.
Cost controlPer-user daily limits, a cap on files per call, and a duplicate cache keyed on the file’s content hash. The cache stores the reviewed result, so re-uploading a corrected bill costs no tokens and restores the correction.
Notice ReplyOne call returns a summary and a response plan. The model receives only the notice and a catalogue of field names; it returns references that the app resolves to the client’s real figures on the device, so no client financial data reaches the model.
HSN suggestionA single low-temperature call that suggests an HSN/SAC code from an item description and flags a mismatch between the name and the code.

Measuring the OCR

I built an eval harness that generates bills whose correct answers are known by construction, renders each as a clean PDF and as a scanned copy, and slices the prompt straight out of the deployed function so the test cannot drift from what ships.

  • Result: raising the image resolution lifted purchase-bill accuracy from 97.1% to 99.4%, and sales-bill accuracy from 96.2% to 98.2%, on scanned PDFs.
  • Measured and kept or rejected: removing the zero-temperature setting cost 2.6 points, so it stays; a lower thinking level truncated the JSON output on three of seven bills, so it was rejected.
  • Wiring check: an end-to-end script reads token counts back from the deployed function, proving the setting actually shipped.
  • The honest limit: the set is seven clean, machine-generated bills. It shows the method works and that the change helped; it is not a claim about accuracy on real-world bills, which I have not yet measured.

Two-step sign-in

Added without a way to lock a firm out: the design fails open on unknown state and enforces on the server — the client gate is only a convenience.

  • Per-firm switch with a grace period before it becomes mandatory, using authenticator-app codes.
  • Enforced where it counts: built into the Firestore role checks and into the callable functions, not just the sign-in screen.
  • Recovery through single-use, hashed recovery codes; a partner can reset a colleague only after re-entering their own password; every new authenticator is logged and emailed to its owner.
  • Proven against the emulators and a live development project with real tokens before it touched production.

Engineering decisions

  • Reconcile and flag, never silently fix. When a GST figure disagrees with its parts, the system raises a visible, reversible flag instead of quietly correcting a number that goes into a return.
  • Two audit trails on purpose. A client-written log can be tampered with; a server-written one cannot. Every write also carries its author, guarded against framing a colleague.
  • Derive at read for discounts. A trade discount reduces the taxable value, so documents keep gross figures and every consumer nets them at read time — because the netting steps are not all idempotent, and applying one twice would understate a return.
  • A lesson from one shared component. A change to a shared GST-rate picker once emptied nine dropdowns while the build, lint and its own test all passed. Tests now mount the real pages that consume a shared component.
  • Safe deploys. Hosting ships only through CI, and a hook refuses any build wired to the wrong project; functions deploy by name, one at a time.

Quality

Over 4,900 automated tests pass today, alongside several hundred emulator-backed security-rules tests.

Rules testsFirestore and Storage rules are exercised on the emulator, including the role matrix and the two-step enforcement.
Real-shell testsSeveral tests boot the actual app shell signed in as a chosen role, which caught a route that a unit test had missed.
CI gatesRules tests, a lint ratchet, type-checking, unit tests, a build, and per-chunk bundle-size budgets all gate every deploy, along with a guard that fails the build if a credential file is ever tracked.

Outcome

Quillix is live and in use at a chartered-accountancy firm, covering the cycle from bill capture through GST return preparation to Tally export — with server-enforced access control, a tamper-resistant audit trail, and a measured approach to its AI components.

Being straight about scope: it is in use at one firm and has not been load-tested; the OCR figures above are from a synthetic evaluation set; billing is built but switched off; and the Windows desktop shell is not yet distributed. The source repository is private, and I never name the firm.
